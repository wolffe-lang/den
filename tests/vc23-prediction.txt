P1. What holds memory today on a large pack, by component (file://; https
adds its two body copies):
  a. transport.message: the whole pkt-line response F in one growing List
     in the ambient region (each doubling leaves its old buffer), and
     every packet's own payload, never reclaimed: about 3F to 4F.
  b. wire.parse_pack: a decoded copy of every payload and the appended
     pack P, growing by doubling: about 3P.
  c. pack.stream_entries, run twice (stream_refs, then decode): each entry
     inflates `data[pos..]`, a copy of the rest of the pack, so the copies
     sum to about entries x P / 2 per run; plus a copy of every inflated
     body (U, the sum of object sizes).
  d. pack.decode: a copy of every entry on every resolution pass and the
     resolved bodies: at least 2U.
  e. loose installation: one compressed copy per object, ambient.
  f. the closure check: per-object reads in regions, reclaimed, but an
     aggregate 128 MiB cap on bodies read, and every blob is read.
  g. checkout: every target blob read twice outside any region, and each
     written file read back for the index: about 3 x the worktree.
  Over https: the response body (F, read per region since vc22) and its
  returned copy (F).
  So today's peak is tens of times the pack, as measured; the 140,000,000
  wire cap and the 128 MiB payload caps are the only thing keeping it
  inside a container, and den's own repository cannot pass them.

P2. The streaming design and its bound:
  - Receive: the fetch response is read one pkt-line at a time, each in
    its own region; band 1 goes straight to an exclusively created
    temporary under objects/pack, band 2 is dropped, band 3 is fatal.
    HTTP bodies stream through the connection's one reused 64 KiB buffer
    (Content-Length or chunked). No whole response, body or pack is held.
    The fetch no longer asks for thin-pack, so the received pack is
    self-contained and installed as it is (git-index-pack(1) appends
    missing bases instead; den does not need to).
  - Index (pass 1, sequential): each entry is read from the file by
    offset into a window sized from its declared size and grown by
    doubling only when the inflater reports truncation; whole objects are
    inflated into a list reserved to their exact size and hashed; deltas
    are inflated to check their size and record their base. The CRC-32
    and the pack's SHA-1 are computed over the same bytes. One entry's
    window and body live in one region: about 2.1 x that object.
  - Resolve (pass 2): a depth-first walk from every whole object over its
    OFS and REF children. The bodies on the walk's path are bounded by
    W = 96 MiB (git-config(1)'s core.deltaBaseCacheLimit default); a
    child that would cross W is resolved and named, and its own subtree is
    revisited later from a fresh reconstruction (base, delta and result,
    at most three bodies at once). Delta outputs are reserved to their
    declared size.
  - Per-object metadata (offset, length, CRC, kind, size, base, parent,
    name) and the idx (28 bytes an object): about 160 bytes an object.
  - The connectivity check walks commits, trees and tags; blob types come
    from the indexer's table, so no blob body is read.
  - Checkout: one file at a time in its own region; the pack reader's
    copies make about 5 x that blob.
  Bound: peak RSS <= 64 MiB + W + 5 x L + 160 bytes x objects, where L is
  the largest object (indexing) or largest checked-out blob (checkout).
  Predicted: den's own repository about 230 MiB (pass 1 on its 98 MiB
  whole blob; bound 652 MiB); the large fixture below (48 MiB blobs at
  HEAD) about 300 MiB (checkout; bound 400 MiB). Disk: the pack once, as
  git keeps it, plus the idx.

P3. Time for den's own repository over https: den receives at the link's
  rate (2.13 s of CPU for 140 MB of TLS today), then inflates about
  378 MB (about 70 MB/s, vc01's release figure) and hashes the same with
  SHA-1 (about 65 MB/s, vc18's), then checks out 339 MB (a second inflate
  and SHA-1 for the index). Expect about 30 s of release CPU and twice
  that natively: den about 165 s release and 220 s native, against git's
  130 s on the same link, so 1.3x and 1.7x. On a fast link the ratio
  grows toward den's CPU against git's (git used about 4 s of CPU).

P5. The URL off argv (R-vc22b-1 (a)): Git does not keep a configured
  remote's URL off argv over https. Measured black-box with GIT_TRACE: for
  `git ls-remote live` with remote.live.url from GIT_CONFIG_*, git starts
  `git remote-https live <URL>`, as gitremote-helpers(7) describes. So
  the push row stops using Git against the private fixture: den takes the
  URL from a remote configured after `den init` through GIT_CONFIG_*
  (fetch and push by name), and the pushed branch is checked in-process
  by the row against the server's own ref advertisement. A watcher reads
  /proc/<pid>/cmdline of every descendant while the row runs and fails if
  the URL or token appears; red on trunk's tools/http-live-test.py (the
  URL is on den's and git's argv). R-vc23-3 records the choice.

P6. den#66: the witness is in the field leg's evidence. In the failing
  m2-commit-paragraphs row, Git's snapshot holds
  .git/objects/maintenance.lock (empty, 0644) and den's does not; the
  index differs only in stat fields the index proof canonicalizes and the
  loose object only in its zlib bytes. Git's commit starts automatic
  maintenance detached (git-config(1) maintenance.autoDetach defaults to
  true), and the harness can snapshot while the detached child holds its
  lock. Expect the pinned environment's maintenance.autoDetach=false to
  join that work before the command returns, so the lock never appears,
  with every oracle row unchanged. A repeat count on the Mac with
  Homebrew's Git shows the lock before and none after.

P7. Rulings: R-vc23-1 the wire cap: recommend (A), remove the whole-pack
  cap: memory no longer scales with the pack, and the disk check is the
  write itself (a failed write refuses by name and removes the
  temporary). R-vc23-2 the per-object cap: recommend 512 MiB,
  core.bigFileThreshold's default, the size above which Git itself stops
  treating an object as an in-memory delta candidate; at the cap the P2
  bound is about 2.7 GiB, inside a 6 GiB container. The pack reader's
  16 MiB object cap rises to the same value, or a clone could not check
  out what it indexed (den's HEAD has 19.9 MB blobs). The object count
  follows the idx reader's existing 400,000 cap, and delta depth stays at
  the reader's 64 (den's own deepest chain is 29).
